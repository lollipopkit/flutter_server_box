# CLAUDE.md

ServerBox Monitor: the agent (Rust, ntex, SQLite) that samples a machine, raises alerts, and serves the API and the Svelte panel. Part of the ServerBox monorepo (root `../CLAUDE.md`).

## Commands

```bash
cargo run                                   # serve on 0.0.0.0:3770; cp .env.example .env first
cargo test                                  # all backend tests (--test <name> for one)
cd frontend && npm run dev                  # panel on :3000, proxies /api (and the ws) to :3770
cd frontend && npm run build                # typesafe-i18n + svelte-check + vite build
cd frontend && npx vitest run               # run vitest from frontend/: from the repo root it picks up third_party/ironrdp and fails
cargo sqlx migrate run / cargo sqlx prepare # migrations; offline query cache in .sqlx/
```

## Layout

- `../crates/sbm_parser/`: commands, scripts and parsers shared with the app over FFI. Pure, no IO. `capabilities::capabilities(system)` says per `ServerStatus` field whether a platform collects it; check it before calling an empty field a bug.
- `../crates/sbm_native/`: monitor-only native sampler (`sample(state, system)`, always on the one `native-sampler` thread, `monitoring::NativeSampler`: Windows' sysinfo components are thread-bound WMI objects): cpu/mem/swap/disks/diskio/net/uptime/host/sys via `sysinfo` or procfs, feeding `sbm_parser::linux::parse_*` unchanged. NVIDIA (`nvidia-smi`) and Linux AMD/Intel (shared DRM command) run every cycle; sensors, batteries, SMART and legacy Windows AMD on the extended cycle via the script. `monitoring.rs::collect_metrics` merges them.
- `src/`: `cli/` (`serve`, `config`, `cleanup`), `core/` (config, `remote_access.rs`, `fs_roots.rs`, `config_file.rs`), `api/` (handlers, `authz.rs`, `ratelimit.rs`, `ws/`; `server.rs` the route table, with `server/{state,login,metrics,settings}.rs`; `respond.rs` the error answers: `{"error": code}`, a cause logged and never sent, `config_unreadable`; the `require!` macro in `api/mod.rs`), `pty.rs` (the terminal's shell on a local PTY), `monitoring/` (the sampling loop in `monitoring.rs`, `metrics.rs`, `script.rs`, `adapt.rs`; `rules.rs`, `push.rs`, `custom_cmds`), `utils/lock.rs` (`LockExt`/`RwLockExt`: std locks taken through a poisoning), `db/` (migrations, retention cleanup). Filesystem work a handler does goes through `spawn_blocking` (`config_file::read_async`/`write_async`, container backups' listing and removal).
- `src/stacks/`: the web apps the agent deploys with Docker Compose; their catalog is `../store/apps/<publisher>.<name>/` (`manifest.toml` + compose files, `docs/schemas/monitor-app.schema.json`), read and checked by `stacks::manifest` (its test reads every folder there). Adding one: the `serverbox-webapp` skill.
- `frontend/src/`: Svelte 5 runes, Tailwind 4 (class-driven dark), no router (`layout.svelte.ts`). `pages/`, `components/`, `lib/` (API client, rune stores, `terminal.svelte.ts`), `types/`, `i18n/` (15 locales). Tests: vitest + testing-library; svelte-check is the type gate.

### Cross-platform semantics left as is (changing them would change stored history)

- `cpu`: Linux cumulative ticks; BSD an instantaneous percentage in the tick fields; Windows a percentage accumulated into a synthetic counter. `monitoring::adapt_cpu` branches on `SystemType`; any new consumer must too. The native sampler has consistent semantics; the script path keeps the split.
- `sys`: a real distro parser on Linux (`PRETTY_NAME`); BSD/Windows reuse `parse_hostname` on `uname -or`/`OsName`. `os_id`/`os_id_like` are Linux-only (`/etc/os-release`).
- `uptime`: Linux/BSD normalised by `parse_uptime`; Windows passes PowerShell's string through.
- `diskio` is cumulative 512-byte counters on both paths.

## Panel

- **The panel is a desk** (a macOS-style web desktop, every feature an app in a window): `frontend/src/desk/CLAUDE.md`.
- **State and UI only.** The panel never composes a shell command or parses output: it calls an agent endpoint, which builds and parses through `sbm_parser` (the app reaches the same functions over FFI). Sending text to `/exec` and parsing it in TypeScript is ruled out.
- First load: one locale's dictionary (`i18n/init.ts`, `ready` before mount; tests load all), and `/assets/{name}` (`api/assets.rs`) serves the hashed build output `immutable`, as the `.br`/`.gz` copies `npm run build` writes (`scripts/compress.mjs`); `/desk-app/{name}` the design system installed apps load (`dist/desk-app`, any origin, see `docs/dev/desk-sys.md` UI). The 3 MB icon font is most of what is left.
- The terminal store (`lib/terminal.svelte.ts`) owns protocol and reconnect and knows nothing about xterm.js; xterm is a dynamic import (`lib/xterm.ts`). Dialog terminals (`TargetTerminal`) use `persist: false` and `close()` on destroy, never the page's stored handle. An explicit open forgets the stored handle; only Resume rejoins it.
- An answer that arrives after the sidebar switched servers is dropped (`stale(serverId)` pattern); anything that writes binds to the server it was opened on.
- Multi-server: a server list (URL + session) in localStorage. Served by an agent (same origin) or hosted statically talking to several agents.
  - **A panel an agent serves holds only that server** (`ServersStore.servedByAgent`): decided at startup by `confirmSameOrigin()`'s probe (assumed until it answers; `unreachable` counts as the agent's own). `add()` is refused and both add affordances are absent there.
  - The vite dev server proxies to an agent, so the probe would answer "own"; `import.meta.env.DEV` exempts it (no shipped build has it).

### Cloudflare Pages

- Root directory `monitor/frontend`, build `npm run build`, output `dist`. The panel imports `monitor/sdk/serverbox-desk/src` (the app bridge's protocol), so the build needs the repository, not `monitor/frontend` alone; keep build steps in `package.json`, not in a dashboard. Repo-root variant: `cd monitor/frontend && npm ci && npm run build`, output `monitor/frontend/dist`.
- `frontend/.node-version` pins Node 24 (Pages reads it from the root directory); the Dockerfile (`node:24-alpine`) and `monitor-release.yml` match. vite 8 needs `^20.19.0 || >=22.12.0`.
- Each agent must allow the origin (`cors_allowed_origins` / `SBM_CORS_ORIGINS`) and be reachable over HTTPS (built-in TLS or a proxy/tunnel). Without `frontend/dist` the API runs alone.

## Access (`docs/dev/monitor-permissions.md` is the contract)

- **One account, signed in with its password alone; it may do what the system account the agent runs as may do.** No roles, grants, file roots or read-only mode: where it is installed decides the reach. `config.toml` keeps only the machine side: `ssh_addr`, limits, and `allow_insecure` (acting needs TLS or a loopback peer otherwise; legacy `terminal.allow_insecure` / `fs.allow_insecure` count as it, TODO remove). Retired keys (`full_access`, `listen_public`, `terminal.enabled`, `fs.enabled`, `fs.roots`) restrict nothing; `RemoteAccessConfig::retired_keys` names them in a startup warning (TODO remove).
- `api/authz.rs` is the one place a request becomes a `Caller` (JWT → the account); `Caller::check(state, secure)` is the transport rule; `capabilities.access` answers it. Every route that acts on or configures the machine or the agent takes `authz::acting_caller` (or `machine::gate`, which also audits a refusal); `jwt_caller` alone is for the desk's own state (preferences, themes, notifications) and lists. `tests/permissions_api.rs::a_plaintext_link_only_reads` holds the list. JWT `sub` is `auth::SUBJECT`; a token from before `users.password_changed_ms` is 401 (migration 034 moved it, so no token from before the one account counts).
- Password change (`PUT /me/password`, CLI `password`): `password_changed_ms` moves, watch tokens deleted, `authz::end_account` closes sessions, tickets, Agent mode tasks, proxies, relays and listeners (`password_changed`). Some changes re-ask the password (`admin::reauth`). Login throttle (`api::ratelimit`): the address plus who is asking (`Who`): a known device (`login_device`, migration 033; the login answers a new `device` token, the clients send it back) on its own counter, strangers on a shared one (20 free), reauth on its own, so strangers cannot lock out a device that signed in before; a password change forgets every device.
- Every sign-in is audited (`Kind::Login`: address and `device known`/`new device`/`wrong password`/`throttled`). The login's optional `name` (else the User-Agent, 80 chars) labels the device in `/live`.
- Migration 032 merged older multi-account databases into the oldest admin. `tests/permissions_api.rs` covers sign-in and reach; `tests/watch_token_scope.rs` lists routes with requests harmless under the panel login (`/power` excluded).

## Endpoints

### What the Monitor tab reads (`alerts`, `audit`, `live` in `FEATURES`)

- `GET /alerts` (`api::desk`): `DeskHub` keeps the rules firing at the last check with `since` (in memory) from `rules::Firing` (rule, type, matcher, threshold, formatted value; `message` is what was pushed). Any panel token.
- `GET /audit` (`api::audit_log`): `access_log` newest first, paged by `before` id, filtered by one `kind` (`audit::Kind::ALL`) and `result`. Acting rule.
- `/live*` (`api::live`): `GET` lists terminal sessions (`SessionStore::list`, the public half of the handle; `what` is the audit detail), connections (`ws::live::LiveConnections`), watch tokens and `login_device` rows (never a token). A relay, listener, virt console or RDP session registers when it starts carrying bytes and its loop waits on the returned `Ending`, which also delivers `AppState.password_changed`: `Signal::Changed` re-checks the caller as before, `Signal::Ended` (`DELETE /live/connections/{id}`) closes with `ended`; dropping the `Ending` unlists it. `DELETE /live/sessions/{id}` is `SessionStore::close`; `DELETE /live/devices/{id}` forgets a device (not a sign-out: the password is what keeps one out). Acting rule, endings audited (`Kind::Admin`).
- An unmatched `/api/v1/*` path is a JSON 404 (the scope's `default_service`), never the panel's `index.html`.
- An answer given before the request's body was read to its end reads the rest first (`api::unread_body`, on `/api/v1`: at most 1 MiB and 5 s, past either `Connection: close`): unread, ntex drops the connection under a client still writing (seen as the connection gone) and marks the answer `close` only when the body went first. A test server that builds its own `/api/v1` scope adds it too.
- Updating an agent: `sbm_parser::monitor_agent` (release page parsing, `outdated`, `install_kind`, `upgrade_command()`, `start_update_script()`, `read_update_log`), shared by the agent and the app (FFI; the app reads GitHub itself only for an agent too old to answer). `install.sh upgrade` with no mode detects user unit / system unit / OpenRC, reruns itself through sudo for the latter two, refuses when nothing is installed (Docker); it renames new files over the running ones and restarts last with SIGHUP ignored.
- `/update` (`api::update`, feature `update`): `GET` `{version, latest, checked_at, error?, outdated, install, command?, needs_password, run?}`; `command` only for `install: script` (binary at `*/server-box-monitor/server_box_monitor`, not in a container or `/nix/store`). Releases read with `desk_themes::HttpFetch` (sets a User-Agent, which GitHub's API requires) every 12 h and on `?check=1` (≥ 60 s apart; a failed read keeps the version found before, with `error`); a newer version leaves one `agent.update` notice after a read (`Source::Agent`, deduped by `params.version` under a lock). **`POST /update/run` never runs the upgrade as the agent's child**: the start script runs it as `systemd-run [--user]` (outside the agent's cgroup, which a restart empties) or `setsid`, output to `update.log` in the working directory between start/exit marks, which the agent that comes back reads as `run`; OpenRC without root takes sudo's password on the script's stdin (tried first, `SUDO_REFUSED_EXIT` → `403 sudo_password`). `SBM_INSTALLER` / `SBM_INSTALL_PKG` in the agent's environment point it at a local installer and package. Clients (panel `desk/apps/settings/AgentUpdate.svelte`, app `view/page/monitor/update_agent.dart`) start it and poll `GET /update`, a failed poll meaning "restarting". An agent too old to sign in to (`MonitorHttpErrType.agentTooOld`, its 400/422 names `username`) is started by the app through its `/exec` with the same script, signed in to with `MonitorHttpCredential.legacyUser` (the `monitor_user` column and backup `user` the app kept, sent with every login so such an agent stays reachable until updated; TODO remove). `tests/update_api.rs`; **`scripts/monitor-upgrade-e2e.sh <node>`** installs a user and a system service on a fresh PVE VM and has each update itself through the API (`scripts/monitor-upgrade-e2e.py` follows it across the restart).

### `POST /api/v1/exec`

One command → `{exit_code, stdout, stderr, truncated, timed_out}`; in: `{cmd, stdin?, env?}` (`stdin` carries a sudo password, `env` avoids quoting). Not a terminal frame: a PTY is shared with the user's typing (`terminal.rs` rejects an `exec` frame, tested). **Timeout, output cap and request-body limit are `[remote_access.exec]`**: the operator's trade, never raised per request or per action; the body limit is passed to `configure_api` because ntex applies it before handlers. Work that must outlive it starts detached and is polled. `tests/exec_api.rs`.

### Machine endpoints (`api/machine.rs`, issue #1623)

Shared rules:
- The command is built in Rust (`sbm_parser`, the app's text where one exists) and run through `api::exec::run`, so `[remote_access.exec]` bounds it.
- `machine::gate` is the one place the transport rule is asked and a refusal recorded (`gate_as` for a route with an audit kind of its own: `/exec`, `/fs`, custom commands, Agent mode); the refusal is `403 {"error":"forbidden","message"}` everywhere. Audit rows are `Kind::Machine`, detail the feature and verb, never a password, value or output.
- Script text runs via `machine::as_self` (`sh`, text on stdin) or `machine::as_root` (`sudo -S -p '' sh -c "$SBM_ROOT_SCRIPT"` with only the password on stdin, or `sudo -n`): the script never shares the password's stream. A rejected password is `sudo_rejected` (`sbm_parser::script::sudo_password_rejected`), not a status. A script carrying a secret uses `machine::as_root_private` (0600 file, only its path on the command line).
- Outputs reach parsers as `CommandOutput` via `machine::command_output` (timeout and cap are failures with a reason).
- `machine::FEATURES` is `features` in `/capabilities`; a panel offers a page or a terminal target only when listed (older agents 404 or ignore unknown fields).
- Tests never perform the real action on the machine running them (`power`, `cron` save, firewall changes, user changes, benchmark runs).

Per endpoint:
- `/power`: the status script's `SbShutdown`/`SbReboot`/`SbSuspend` via `monitoring::local_script_command`. `tests/power_api.rs` checks refusals and records only.
- `/process` (`sbm_parser::proc`, `PsView`): the script's `SbProcess` with ≥ 8 MiB output, kept in `AppState.process_sample` (reused within 2 s, baseline 30 s); a stop checks the PID's start identity, retries as root on `denied`.
- `/services` (`sbm_parser::service`): systemd, procd, OpenRC; an action names a unit by its listing key, resolved against a listing read for that request, which also decides whether root is needed.
- `/cron` (`sbm_parser::cron`): the agent account's crontab; an edit is one operation on one line by listing index, applied to the file re-read at write time via `crontab -`; a stale index is `unknownLine`. Audit has the schedule, never the command.
- `/containers` (`sbm_parser::container`): Docker then Podman (a `docker` that is Podman is read as Podman); each part (containers, images, usage, logs) is one batch split by a fresh separator; an action answers with the refreshed listing (images for image actions; each image carries `dangling` and `reference`, `ContainerImage::reference`, what a client names it by). `ContainerAction` covers lifecycle, `remove_image`, `pull_image`, `prune_images`, `prune_system`, `run` (`run`'s args split by `parse_run_args`). Values are validated and used trimmed; a bad one is `400 {"error":"invalid_input","issue":<code>}` before the runtime is probed. `unused_tagged` is computed by the agent. No runtime access is `permission_denied`. A shell inside a container is the terminal `target` (`container_exec`). TODO: `DOCKER_HOST`, sudo path.
- `/tmux` (`api/tmux.rs`, `sbm_parser::tmux`): sessions (`created`/`last_attached`/`activity` are epoch seconds or null; tmux ≥ 3.6 dropped the `*_string` variables), `available: false` when not installed (found by the agent's `FIND_COMMAND`, never named by the client), "no server running" is an empty list, a failed listing carries `error`. Attaching is the terminal `target` (`tmux`). Limitation: a tmux server first started from the panel lives in the agent's cgroup, so with systemd's default `KillMode=control-group` an agent restart ends it.
- `/benchmark` (`sbm_parser::bench`): the agent owns the run: the `benchmark_run` row (migration 012) is written before the detached launcher starts and `start_poller` (from `cli::serve`) finishes it with or without a page. One run at a time is a partial unique index. Script `assets/yabs.b64` embedded (`tests/benchmark_asset.rs`). Linux only.
- `/system-users` (`sbm_parser::users`): the machine's accounts. Linux only; a write is resolved against a fresh listing; root and the agent's own account are refused; a password write uses `as_root_private`.
- `/firewall` (`sbm_parser::firewall`): ufw or firewalld, Linux only. `POST /firewall` reads (sudo password in the body) and reports what reaches each way in (the panel's connection unless `proxied`, and SSH). A change is one `UfwChange`/`FirewalldChange`: `/firewall/plan` returns the `Plan` and runs nothing; `/firewall/act` re-reads, re-plans and runs that (keep-open rules first when asked). A plan carries `plan_id` (a digest); a plan that asks runs only under the confirmed id, otherwise `confirm_required` with the new plan. The app uses the same `ufw_plan`/`firewalld_plan`.
- `/snippets` (`sbm_parser::snippet`, migration 013): PUT replaces the library (refused per row `{error, index}`); `POST /snippets/plan` expands a script into steps and runs nothing; the panel sends an empty context, so `${host}`-style keys are `{error:"unanswerable", key}`. Audit names snippets only.
- `/desktops` (migration 014): routes validated by `sbm_parser::desktop`; no password stored (asked per session, given to noVNC only). VNC over `/stream/ws` (`RelayChannel` in `lib/desktop.svelte.ts`). RDP over `/rdp/ws` (`api/ws/rdcleanpath.rs`): the agent is the RDCleanPath proxy (ticket in `proxy_auth`, purpose `rdp`; server certificate captured, not verified). **The RDP session, NLA credential included, is plaintext in the agent**; the panel says so. `tests/rdp_ws.rs`.
- `/bmc` (`sbm_redfish`, migration 016): targets so an agent reaches neighbours' BMCs. Password write-only (`has_password`; `null` keeps, by id). **No pinned certificate, no dial** (`require_pin`); one login per request; upstream failure is `502 {error:"bmc", failure}`, never 401. `GET /bmc/{id}` returns `intents` (`ResetRequest::build`). `tests/bmc_api.rs` (fake Redfish).
- `/virt` (`sbm_virt`, `api/virt*.rs`): guests on PVE or libvirt in `sbm_virt::model` terms. Loads are POSTs (a libvirt sudo password goes in the body, never stored). PVE: one stored config (migration 017; `password`, `token_secret` write-only) and **one `sbm_virt::pve::Client` in `AppState.virt`** (tickets live 2 h; `POST /virt/pve/tfa` answers a waiting login); an unvouched certificate is `cert_unconfirmed` until `POST /virt/pve/cert` pins it. A host failure is 200 with `error` (its `needs_input`, `VirtError::needs_input`, says it waits for the operator, so a client stops refreshing on it). Consoles are resolved before the socket opens: `POST /virt/console` mints a `Purpose::Virt` ticket (30 s, refused by `/ws-ticket`) and `/virt/console/ws` relays in `/stream/ws` framing; PVE tickets never reach the browser; a libvirt serial console answers the `virsh console` command for the panel terminal. Snapshots, storage/networks (`virt_resources.rs`; PVE asks the node which interfaces are live via `LIVE_NET_SCRIPT` so the operator's link is never edited), guests (`virt_guests.rs`), hardware and cloud-init (`virt_hardware.rs`, `revision` per read, stale = `conflict`), backups (`virt_backups.rs`, PVE only): each refused as its `Detail::*Refused`. `tests/virt_api.rs` (fake PVE over TLS).
- `/container-backups` (`container_backups.rs`, `sbm_parser::container_backup`; restore and delete re-ask the password): a container's or its compose project's volumes and bound folders, each `tar czf` from inside an `alpine` container into `<database dir>/container-backups/<id>/` (a protected tree) with `meta.json`; containers stopped meanwhile when asked and started again whatever happens; restore stops the containers still there (by name), empties each mount and unpacks it. Bound system folders (`/`, `/etc`, …) and bound files are never archived nor written back (`skipped`). One job at a time (`stacks::job`). Real-Docker round trip in `tests/stacks_docker.rs`. Where they may go is `GET /container-backups/destinations` (`storage::backup_destinations`: mounted filesystems outside where the system lives, with what is free; the panel offers those). Where they go is `PUT /container-backups/settings` (migration 027: a destination folder, a backup disk's mount, `serverbox-container-backups/` made in it and protected at run time, `fs_roots::protect_at_runtime`; `keep` per label, the oldest pruned after each backup). Schedules (`/container-backups/schedules`, daily/weekly at the machine's time, by container name) run from `container_backups::start`'s minute loop, one at a time. A backup is refused (`507 notEnoughSpace`) when `du` of its mounts (from a throwaway container) exceeds the destination's free space, and (`409 destinationMissing`) when a backup disk's folder is gone (unmounted): never written into the folder under it.
- `/storage` (`api/storage.rs`, `sbm_parser::storage`, Linux): `lsblk` tree (a pool's `scanning`: a scrub or resilver running) + `busy` (`storage::in_use`: mounted, swap, a member of an array in `/proc/mdstat` or a pool in `zpool status -P`, LVM, read only, a firmware partition (EFI, BIOS boot, MS reserved, by `PARTTYPE`); an old signature whose array or pool is gone is free), `system` (devices mounted where the system lives: `/`, `/boot/efi`, …; never unmounted, `systemMount`), md arrays, ZFS pools, the tools present. `POST /storage/act` takes one `StorageAction` (partition a whole disk GPT, format ext4/xfs/btrfs, mount with an `/etc/fstab` line by UUID and `nofail` (backed up to `fstab.sbm-bak`) and optionally owned by the agent's account, unmount, md create/add/remove/delete with `mdadm.conf`, zpool create/scrub/destroy, SMART self-test), checks what it consumes against a fresh listing (a disk and its own partition together are `overlapping`), tries the sudo password, and runs the script as root as a job (`Job::run_root`). Also grow a RAID 1/5/6 by one working member, expand a mounted ext/xfs/btrfs (`storage::growable`), grow a partition into free space after it (`sfdisk -N`, `partx -u`), add a vdev or a spare to a pool, replace/attach/online a pool's device, remove a spare or cache (`Vdev::section`; pools are created `autoexpand=on`), format inside LUKS2 and lock/unlock (`luks-<uuid>`; the passphrase is a 0600 key file `PrivateScript` kept until the job ends, never in the script or the audit, `ActBody::passphrase`). **The view and every check are `storage::parse_view` / `storage::check`** (one `view_command`), shared with the app's FFI (`sbm_ffi::api::storage`, which writes the passphrase into a key file the script makes itself: `script_with_passphrase`). SMART: `POST /storage/health` reads every disk as root (`storage::HEALTH_COMMAND`, `DiskHealth`: `supported` false for virtual disks, which get no test button), kept in `StorageJobs` for `GET /storage`'s `health`; a self-test job re-reads it with its password. `storage_watch` (migration 028): the maintenance schedule (scrub/md check, SMART short/long; `PUT /storage/maintenance`, `POST …/{task}/run`) and the watch (arrays, pools every 5 min, SMART hourly), both unattended: `storage::UNATTENDED` puts `sudo -n` before each privileged command, so a narrow sudoers rule (`smartctl`, `zpool scrub`, `mdadm --action=check`) is enough; a refusal is `sudoNeedsPassword`. What turns bad is a desk notification (`Source::Storage`, kinds `storage.*`, `desk/noticeText.ts`) and a push (`monitoring::push::push_all`). `tests/storage_e2e.rs` drives it on loop devices as root (`SBM_E2E_STORAGE=1`; t10 has mdadm; ZFS needs zfsutils); `frontend/e2e/storage.e2e.ts` drives the panel (Playwright, `npx playwright test storage`, variables in its header). **`scripts/storage-e2e.sh <node>` runs all four storage/sharing e2e on a fresh PVE VM** (`scripts/e2e-vm.sh`: a linked clone of template 9310 with empty disks hot-plugged by serial `sbmdisk*`, destroyed after; one-time `e2e-vm.sh template <node>`), never on an existing machine.
- `/shares` (`api/shares.rs`, `sbm_parser::shares`, Linux): SMB (Samba) and NFS. ServerBox's shares live in its own files, rewritten whole (`/etc/samba/serverbox.conf`, included once at the end of `smb.conf`; `/etc/exports.d/serverbox.exports`); others are listed `managed: false` and left alone. `PUT /shares/smb` / `/shares/nfs` take the whole managed list, checked in Rust (no line breaks, names, paths, clients), written as root, checked (`testparm`, `exportfs -ra`) with the previous file put back on refusal (`EXIT_REFUSED`, `EXIT_NOT_A_FOLDER`); SMB passwords through `as_root_private` (`smbpasswd -s`); Time Machine (`fruit`) and a recycle bin (`vfs_recycle`) per share; `POST /shares/connections` (root: `smbstatus -j`, NFS peers from `ss`); installing Samba / the NFS server is a job (`JobKind::Shares`). The app reaches the same through `sbm_ffi::api::shares`. `tests/shares_e2e.rs` (root, `SBM_E2E_SHARES=1`, both installed), `frontend/e2e/sharing.e2e.ts`.
- `/backup` (migration 020): opaque blobs (files, `core::blobs`) for the app's `MonitorBackupStorage` and the panel; the app encrypts first. `MAX_BYTES`, `MAX_BLOBS`; names `[A-Za-z0-9._-]`, no leading dot.

### `/api/v1/stacks*` (web apps, `stacks/`, `api/stacks.rs`, migration 024)

- An app is a folder `<publisher>.<name>/` (manifest + compose files; the id is made from the two, `core::app_id`, like every app's: the panel's own are `serverbox.*`, a package's `<publisher>.<name>` too). **Where they come from is `stacks::catalog`**, one id one package, in this order: the operator's `[stacks] local_apps` folder (read at start), the store's repositories (`assets/catalog/repos.toml`, each repository tarball's `apps/*`, read at start and hourly, `POST /stacks/refresh` now; cached in `<stacks>/.catalog/`, a protected tree), the shipped ones (`store/apps/`, embedded by `stacks::builtin`, its test holds the list equal to the folders; the Dockerfile copies `store/apps/`). The official repository is `store/` itself (`scripts/store-tarball.sh`), so a catalog change reaches agents without a release. The panel's Immich app (`serverbox.photos`) is `futo.immich`. An app's `title` is its project's own name (`Immich`), never a generic word; `recommended = true` (a handful) is what the desk's first-run guide offers. A test app, `tests/apps/serverbox.testweb` (nginx, two ports, a data folder, a health check), is what `tests/stacks_docker.rs` deploys on a real Docker (`SBM_E2E_DOCKER=1 … -- --ignored`).
- A deployed app is a stack: files and a 0600 `.env` in `<database dir>/stacks/<id>/` (every `stacks/*/.env` is `Protected::in_each`), a `stack` row (settings, never secrets), compose project `sbm-<publisher>-<name>`. Deploy, update, new settings (`PUT /stacks/{id}/settings`, password), start/stop/restart and remove are `stacks::job`s (Agent mode's process-group runner, no exec bounds, lines polled by sequence, cancellable); a stopped agent's `installing` rows fail at start (`stacks::resume`). Deploying, new settings and removing re-ask the password. Before the password the panel calls `POST /stacks/{id}/check` (settings completed, the images the compose files will pull with them, data folders, port) and shows it with the project's metadata (`project`, `developer`, `version`, `homepage`, `source`, licence) for the operator to confirm; the deploy is refused without `acknowledged` (third-party software) and, where the manifest marks `license.accept`, `accept_license`. Removing without `purge` keeps the directory (its `.env` holds the database password); `purge` deletes data paths from inside an `alpine` container (root-owned files) and the images the stack built (`remove_built_images_command`, never one another container uses).
- **What every app shares** (`[stacks] shared_dir`, `shared/` beside the database by default): `{shared}` in a path setting's default (`downloads`, `media/movies`, `media/tv`, `music`, `books`, `comics`, `documents`), never `data`, so a downloader's files are a media server's library; the agent writes `SBM_UID`/`SBM_GID` (the shared folder's owner, the folder made first) `SBM_TZ` (the host's IANA zone) and `SBM_RENDER_GID` (`/dev/dri/renderD128`'s group, else `SBM_GID`) into every `.env` (`manifest::RESERVED`, used by manifests, never set by them). **`[login]`**: how the admin signs in the first time (`user`, `password` naming a `[[secrets]]` entry, `note`); `POST /stacks/{id}/login` (password, audited `reveal`) answers it with the password read from the `.env`, shown in the app's details (`StackLogin`). Agent mode is told every deployed app (`stacks::agent_note`: state, health, loopback address, its exact `compose` command, data folders) in each task's system prompt.
- **Ports** (`stacks::ports`, `Manifest::settle_ports`): TCP and UDP apart (a port setting's `protocol`: `tcp`, `udp`, `both`; 1–65535, the window's port TCP). A port is free when no other container publishes it (running or stopped, `sbm_parser::stack::published_ports_command`) and it binds now or the stack's own running containers hold it; a port the agent may not bind (below 1024, not root) is read from `/proc/net/{tcp,udp}[6]` instead, so `systemd-resolved` on 53 counts; every port setting is checked, against the others too. The dialog suggests the first free one from the default (`PORT_SEARCH`); a deploy moves a suggested port taken since (said in the check's `moved` and the job's log), refuses one chosen outside that range (`409 portTaken` + `field`); start, restart, update and new settings check and never move. Binding cannot see the host from a container or Windows' ports under WSL (`ports::partial`, `ports_partial` in `prepare`). A proxy port taken at start moves to a free one (`start_proxy`).
- **Proxy** (`stacks::proxy`, hyper, its own listener per app on `PROXY_PORTS` 3780–3799, same host and TLS as the API): a window enters with a `Purpose::Proxy` ticket (`POST /stacks/{id}/enter`) at `/__sbm/enter`, which sets the `HttpOnly` `__sbm_<id>` session cookie (12 h; ended by `authz::end_account`, password re-checked every 60 s). Requests are forwarded to the service on loopback without that cookie, WebSockets spliced; `X-Frame-Options` dropped, `frame-ancestors` set to the agent's host and `cors_allowed_origins`; over TLS the service's cookies become `SameSite=None; Secure`. Cookies ignore ports, so proxied apps share a jar. **By host** (`[stacks] apps_url = "https://*.apps.example.com"`, `apps_port` 3779): one more listener takes every app by its `Host` (`futo-immich.apps…` is `futo.immich`; `Hosts`), for an agent behind a reverse proxy or tunnel; `enter` then answers `url`; `Secure` follows `apps_url`'s scheme. Over HTTPS cookies are also `Partitioned` (CHIPS) for a panel on another site; one on the same site as the apps needs neither. `frame-ancestors` adds the origin that asked for the ticket (`Proxies::note_entry`, when `origin_allowed`). `[web] basic_auth` (Transmission): a browser cannot answer basic auth inside the frame, so the proxy adds `Authorization` from `[login]` and the `.env` (`Target::authorization`, sensitive) to a request without its own; it never reaches the browser. `tests/stacks_api.rs` (fake service, no Docker). The app lists deployed apps (the Monitor tab's Web apps section, `AppTab.monitor`, and a server page card) and opens one in the device's browser at the same enter URL (`lib/data/provider/server/web_apps.dart`, `MonitorStackEntry.uri`); the browser keeps its own session, so the app is not in the path.
- **Health** (`stacks::health`, migration 025): every minute each installed app's `compose ps` is judged (`healthy`/`starting`/`unhealthy`/`down`, `stopped` when the operator stopped it, `[compose] jobs` exited 0 are done) and answered in `/stacks` as `health`; a desk notification (`Source::Stack`, `stack:<id>`) says when one goes down or unhealthy, when it is back, and a catalog version newer than the deployed one (once, `update_noticed`). Not judged while a job runs.
- **Built images** (`build:`, when no maintained image exists; AriaNg): a service names a Dockerfile of the package and a `localhost/…` image, context `.` only, no `additional_contexts`/`dockerfile_inline` (`manifest::compose_builds`, mirrored in the skill's `validate.py`), notice `buildsImages`. A deploy or update is `Stack::deploy`: `pull --ignore-buildable`, `build --pull`, `up`. The agent writes a `.dockerignore` of `*` in the stack folder so the `.env` never reaches a build (no package file may be `*.dockerignore`); `check` lists the built images apart (`built`) and the Dockerfiles' `FROM` images among those pulled (`manifest::base_images`).
- Security stance (user's decision): the deploy dialog states what a compose file does (`notices`); nothing is refused or rewritten, except the build rules above, which keep a build to the package and the env file out of it.

### `/api/v1/inference*` (Local inference, `inference/`, `api/inference.rs`)

- What runs a language model here is `sbm_parser::inference`'s: `probe_command` (GPUs with memory and NVIDIA compute capability, Docker and whether it can hand over an NVIDIA GPU, ROCm devices, uv/Python 3.11), `engines` (Ollama, llama.cpp, vLLM, SGLang in containers on Linux; MLX natively on Apple silicon; each with a backend and, when it cannot run, why; Ollama and llama.cpp fall back to the CPU with `cpuBecause` beside a GPU Docker cannot use; vLLM/SGLang CUDA only), `candidates` (what each engine loads of llmfit's models and how it names them; vLLM's memory from the weights' format; on the CPU RAM decides). `GET /inference` (cached 30 s), `POST /inference/recommend` (`useCase`, `allPublishers`: known publishers only by default).
- **llmfit** (`inference/llmfit.rs`): its release `LLMFIT_VERSION` for this platform, fetched on first use into `<database dir>/inference/` (a protected tree) and checked against the SHA-256 compiled into `LLMFIT_ASSETS`; run with `--memory` (a global option, before `recommend`) from the probe, answers kept 10 min. Not linked: its crate embeds 18 MB of data.
- **The container engines are stacks** (`monitor/inference/engines/<id>/`, `stacks::builtin::parts`, catalog `Source::Part`: shipped only, never replaced by the store or `local_apps`, listed with `source: part` and left out of the App Store); deployed, changed and removed through `/stacks/{id}*`. Their manifests have no `[web]` and an `[llm]` (`stacks::manifest::Llm`: port setting, path, model setting, key secret). Models in `{shared}/models` (the Hugging Face cache vLLM and SGLang share, llama.cpp's own).
- **MLX** (`inference/mlx.rs`, macOS): mlx-lm `MLX_LM_VERSION` in `<inference>/mlx/venv` (uv, else python3 ≥ 3.11) installed as a job; the server is the launchd job `MLX_LABEL` of the agent's account on loopback (plist written by `mlx_start_script`, a quoted heredoc), `HF_HOME` the shared Hugging Face cache. Nothing stored: the plist says what it serves.
- **Ollama** (`inference/ollama.rs`): the deployed engine's or the machine's own on `127.0.0.1:11434`; `/inference/ollama/{instance}/models|pull|delete` through Ollama's API, a pull's progress kept in memory.
- **Every model server joins Agent mode** (`inference::providers` → `AgentMode::set_app_providers`, ids `app.<stack>`, `app.mlx`, `app.ollama`; a key from the stack's `.env`, else a placeholder pi needs): worked out at start, after a model server's stack job, MLX start/stop and each `GET /inference`; offered beside the operator's providers (`AppCredentials`), shown in `GET /agent/settings` as `appProviders`, never stored.
- `tests/inference_e2e.rs` (opt-in: `SBM_E2E_INFERENCE=1`, with `SBM_E2E_MLX=1` on a Mac, `SBM_E2E_DOCKER=1` and `SBM_E2E_ENGINES` on Linux): each engine serves a small model and runs an Agent mode task; `frontend/e2e/inference.e2e.ts` the panel's MLX flow.

### `/api/v1/agent*` (Agent mode, `agent_mode/`, migrations 021–023)

- An AI agent works on this machine: pi's durable harness (`pi-durable`/`pi-ai`) run by `fl_pi_llm`'s Rust host (`packages/fl_pi_llm/fl_pi_llm/rust`, feature `reqwest`; a path dependency outside the workspace, so CI, `Dockerfile` and the release check out that submodule). One `Runtime` (QuickJS on its own thread), started on first use; the endpoints' models are listed beside it (`listing`), so only what runs a model waits for them (`ready_runtime`), never a read of a task.
- A task ("flow") is one pi session (a pi-durable SQLite storage, `<database dir>/agent/chats/<id>.db`, `fs_roots::Protected`, the format the apps keep theirs in; a task kept in an older format, `chats/<id>/` or `sessions/`, is removed at start: Agent mode never shipped in them, TODO remove) and one `agent_flow` row (`ON DELETE CASCADE`; sessions without a row are deleted at start by `AgentMode::recover`, which also fails tasks a stopped agent left active). `max_running` run at once, the rest queue; a reply to a finished task runs it again in the same session.
- **What runs unasked** (`agent_mode/tools.rs`, `agent_mode/permissions.rs`, migration 023, `GET/PUT /agent/permissions`): Claude Code's model. The operator's `allow`/`ask`/`deny` command patterns (`sbm_parser::command_rules`: `*` wildcards, compound commands split and wrappers stripped; deny/ask match any part, allow must cover every part and never sees through substitutions or write redirects) come first, deny → ask → allow. Then a read by the model's `effect` and `command_risk::classify`, and a plan the operator approved (word for word). The rest goes by **the task's mode** (`agent_flow.mode`, picked in the composer; absent is the configured `defaultMode`): `manual` asks; `auto` asks the model as a judge (the person's words and the commands run, never output; `hard_deny`/`soft_deny`/`allow`/`environment` prose with `$defaults`, built-ins in `permissions::defaults`): allow runs, block is the tool's failure with the rule, no verdict asks; `bypass` runs it, plans and `Destructive` included, still under deny and ask rules; `disableBypass` refuses starting one and runs an existing one as `manual` (`Permissions::mode_for`). Outside `bypass`, anything `Destructive` asks for the hostname to be typed, whatever the rules. A command's `confirm` carries `allowRule` (`command_rules::suggest`: the one changing part, its first two words then ` *`, else word for word; none behind an ask rule); answering `always` adds it to the allow rules (audited) and runs. Every refusal and auto decision is audited. `sudo: true` runs `sudo -S -k -p ''` with the password on sudo's stdin only (the command's own stdin is `/dev/null`), asked per command, kept in memory 15 min when asked to, never on disk, forgotten when the password changes (`AgentMode::end_account` from `authz::end_account`).
- The transport rule is re-checked before every command (`tools::may_run`). Settings (`agent_settings`, `agent_provider`, `agent_credential`): credentials write-only (`null` removes, absent keeps). Plain HTTP only to loopback or a provider with `allowInsecure`; redirects are not followed.
- Commands run in their own process group (`agent_mode/command.rs`): a stop or a timeout (`timeout_minutes`, default 10, at most 120) ends the group. On Windows they are Windows PowerShell scripts (`-EncodedCommand`, UTF-8 output; the last statement decides the exit code), a stop is `taskkill /T` waited for before the root goes, there is no `sudo` (refused), and the prompts say so (`prompt::shell_note`, `os_name` from sysinfo). Output streams to `/agent/events` (`output`) and is kept in the tool result's `details` (first 2000 and last 8000 lines); the model sees the last 12 000 characters.
- **A copy for pi** (`agent_mode/pi_file.rs`, `agent_settings.pi_sessions`, migration 029, off by default): after every run a task is also written as a session file of pi's coding agent (`Session::export_pi`, session format v3, every version, the current one last) in pi's own directory for the agent's account (`$PI_CODING_AGENT_SESSION_DIR`, or `${PI_CODING_AGENT_DIR:-~/.pi/agent}/sessions/--<cwd>--/`), 0600, so `pi -r` in the agent's working directory lists it; deleting the task deletes it. One way: what `pi` does with it never comes back.
- **Memory** (`agent_mode/memory.rs`, `agent_memory`): the apps' `/memories` files and `memory_*` tools, all from `fl_pi_llm::memory` (the one implementation; the app reaches it over FRB); `AgentMode::memory(user)` is one `host::memory::Memory` so its changes are serial. The index goes into every task's system prompt; the tools run unasked. `GET /agent/memory`, `GET/PUT/DELETE /agent/memory/file?path=` serve Settings → Agent → Memory only, writes audited by path.
- **Files** (`agent_mode/files.rs`): `POST /agent/files?name=` (raw body, ≤ 20 MiB, `Content-Type` kept when it looks like one) waits in `<agent dir>/uploads/`, in memory only, until `POST /agent/flows` names it in `files` (≤ 10; files alone are a prompt); then it moves to `files/<task>/` (0600 in 0700), goes with the task, and the prompt gets an `<attachments>` block (name, type, size, path; text ≤ 16 KiB inline; images ≤ 5 MiB also as pi `ImageContent`), which the agent takes back out of the user message it serves and lists as the message's `attachments` (`files::annotate_entry`, detail and `entry_added` events), the panel showing them as files. Uploads nobody named go after an hour, at start, or when the password changes (`end_account`). `DELETE /agent/files/{id}` drops one.
- **MCP servers** (`agent_mode/mcp.rs`, migration 031, `GET/PUT /agent/mcp`): Streamable HTTP servers whose tools every task gets (`fl_pi_llm::host::mcp`, through Agent mode's `Fetch`: HTTPS, or HTTP on loopback), named `<mcp+fnv(url)>__<tool>` as the app names them, their `instructions` in the system prompt. Headers (a token) are stored like a provider's key: written, never read back (a read names them). Connections are kept (`mcp::Hub`) and made again when a server's settings change or a call fails. Past `fl_pi_llm::mcp::DIRECT_TOOLS_MAX` (24) tools in all, a task gets `mcp_search` (`fl_pi_llm::mcp::search`) and `mcp_call` instead of each tool, so their schemas are not in every request; a call goes through `Gated` as the tool would. A tool annotated `readOnlyHint` runs; any other goes through the task's mode like a `change` command (`manual` confirms, `auto` judges, `bypass` runs and audits). **Deployed apps' servers join on their own** (`stacks::mcp`, migration 036 `stack_mcp`): an app's `[[mcp]]` (`stacks::manifest::Mcp`: the service's own, or a sidecar pinned by digest and published on loopback) is reached at `http://127.0.0.1:<its port setting>`, its header from a `[[secrets]]` entry (read from the app's `.env`), or a token an admin gives (`asked`, `PUT /agent/mcp/apps/{stack}/{index}`, write-only), or OAuth (below); worked out from the deployed app at each connect, so nothing goes stale; an address an admin added wins over an app's. The deploy dialog says whose code a sidecar is (`components/stack/notices.ts` `mcpNotices`). `tests/stacks_mcp_e2e.rs` deploys each catalog app with one on a real Docker, sets it up through its own API and calls a tool (`SBM_E2E_DOCKER=1`, `SBM_E2E_MCP_APPS` picks). **OAuth** (`agent_mode/mcp_oauth.rs`, table `mcp_oauth`): a server that answers 401 is `needsSignIn`; `POST /agent/mcp/oauth/start {url, origin}` (a server Agent mode knows; `origin` is the agent as the browser reaches it) discovers its Protected Resource Metadata (RFC 9728, from the 401's `resource_metadata` or the well-known address) and its authorization server's (RFC 8414), registers (RFC 7591) or names itself by `origin` (Home Assistant's IndieAuth), and answers the authorization URL (PKCE S256, `resource`); `GET /agent/mcp/oauth/callback` takes the browser back with no session, let in by the one-time `state` (10 min), and exchanges the code here, so no token reaches the browser; tokens are refreshed a minute before they run out (a refused refresh forgets the sign-in), never read back (`signedIn` names the servers), `DELETE /agent/mcp/oauth?url=` forgets one. A header an admin set by hand wins.
- **Skills** (`agent_mode/skills.rs`, migration 031, `/agent/skills*`): folders in `<agent dir>/skills/` (`SKILL.md` front matter), installed from a GitHub repository as `npx skills add` takes it (`host::skills::GitHubSource`, the archive from `codeload.github.com`, found as the CLI finds them, `host::skills::find`) or put there by hand; `agent_skill` keeps where each came from and whether it is on. The enabled ones are listed in the system prompt and loaded with the `skill` tool, the app's names and words.
- **Search** (`agent_mode/search.rs`, `POST /agent/search`): the desk's Spotlight asks the agent. The model sorts the text into a keyword, a question or a change (`prompt::SEARCH_KIND`), then a session of its own with `run_command` that refuses anything `command_risk::classify` does not call a read, `report_results` and (for a change) `draft_plan`, which ends the run; it answers with an event stream and stops when the page closes it. Nothing a search runs changes the machine. A search is a session without a row until `POST /agent/search/{id}/task` adopts it as a task (and replies with the text to run it on); one not adopted goes at the next search, after an hour, or at start (`recover`).
- **Model and thinking per task** (migration 030, `agent_flow.model`/`thinking_level`, NULL is the machine's at each run): `POST /agent/flows` and `/reply` take `model` and `thinkingLevel` (`TaskChoice`, checked against `GET /agent/choices`: the models whose provider has a key (pi's `providers.available`), `THINKING_LEVELS`, and the machine's two; never a key); a change while running goes to the open session from its next request.
- `GET /agent/flows` lists newest change first; `?limit=` (≤ `MAX_PAGE`) pages it with `before` = the previous page's `next` (`<updatedAt>|<id>`), `?q=` keeps tasks whose title or line has it (`LIKE`, `%`/`_` escaped); without `limit` it is every task, as the panel reads it. One static statement (NULL turns a condition off).
- `/agent/events`: `text/event-stream` like `/desk/events` (`flow`, `removed`, `pending`, `output`, pi's session events as `event`, `resync`). Audit: `Kind::Agent`, never a password, key or output. `tests/agent_api.rs` (a scripted OpenAI-compatible model).

### `GET/PUT /api/v1/custom-cmds`

Files in `~/.config/server_box/custom_cmds` (`sbm_parser::script`), the same set the app writes over SSH and the status script runs. PUT replaces the whole ordered set (order is the file prefixes). Writing follows the transport rule (a file there runs on every extended cycle); `editable` says whether it holds. Store: `monitoring::custom_cmds` (write-aside-and-rename, names never logged). Outputs ride in `/metrics` (`custom_cmds`, trailing newline kept); the dashboard card shows each command's first line, dropping one trailing line ending for display only.

### `/api/v1/fs/*`

- **The whole filesystem the system account can reach** (`FsRoots::whole_filesystem`). Every path is canonicalised (symlinks followed, `..` refused) and checked component-wise (`core/fs_roots.rs`). Every refusal is the same 403.
- `GET /fs/roots` returns the home directory, then `/` (drive letters on Windows).
- **The agent's own state is never served** (`fs_roots::Protected`, filled in `api::server::agent_state`): DB and journals, the blob directory, `jwt.secret`, first-start credentials, `config.toml` and backups, `.env` files, the TLS key, the custom-commands dir. Per file; hidden from listings; their directories cannot be renamed, removed or chmod-ed. `tests/fs_protected.rs`.
- Writes stream to `<path>.sbm-part-<pid>-<n>` (hidden from listings) and rename, keeping the target's mode; a mode that cannot be carried over fails the write, and the staged copy is removed on every other way out, a dropped request included (`Staged`). `PUT /fs/write?if_version=<version>` (the editor) answers `409 {"error":"modified"}` when the file's `version` (signed nanosecond mtime + size, from `EntryView.version`; a listed link has none, since a write compares the file it resolves to, which `/fs/stat` describes) differs or the file is gone; uploads send none. The check runs after the upload under one lock (`REPLACE`) held through the rename and by `remove`/`rename`, so the agent's own writers cannot interleave; another process can still write in that window (POSIX has no rename-if-unchanged). `modified` stays seconds for the app.
- Known limitation: resolve-then-use is two steps (a symlink swapped between them is followed); closing it needs per-component `openat`+`O_NOFOLLOW`, not portable. `tests/fs_roots.rs`, `tests/fs_write.rs`.

### `/api/v1/desk*` (`api/desk.rs`)

- The panel's desk: preferences (accent, wallpaper `preset:<id>`|`custom`, fit, `background` (absent in a body = on) and `background_denied`, dock, icons as child tables), one custom wallpaper (PNG/JPEG/WebP sniffed from the bytes, ≤8 MiB, ETag = SHA-256), the window session per device, notifications. All keyed by `users.id`, `ON DELETE CASCADE` (migration 018).
- The first-run guide: `desk_onboarding` (migration 035, which marks every account that had preferences or a session), answered as `onboarded_at` in `GET /desk`; `PUT /desk/onboarding` marks it done (the agent's time, the first kept), `DELETE` offers it again. Apart from the preferences, so saving those never brings it back. An agent without the route: the panel keeps the mark in the browser (TODO remove).
- **Session writes are compare-and-swap on `revision`**: the transaction's first statement is the `UPDATE … WHERE revision = expected` (or `INSERT OR IGNORE` from 0), so SQLite's write lock is taken there; a loser gets 409 `{error: conflict, current}`. Never read-then-write. `app_state` is opaque JSON ≤16 KiB.
- `/desk/events`: `text/event-stream` over `fetch` + bearer (not `EventSource`), `data:` JSON lines, `: ping` every 25 s, `{type: resync}` on lag. A hint to refetch, never the only copy. It ends when the password changes.
- Notifications: `DeskHub::rules_checked` gets the firing rules each cycle and stores one per rule that *starts* firing; the newest 500 are kept; read state kept.
- Feature flag `desk` in `machine::FEATURES` covers all of `/desk*` and `/apps*` (they shipped together); a panel without it keeps the desk in the browser.
- `/desk/apps/{app}/storage` (`api/desk_storage.rs`): each desk app's JSON by key; 256 KiB per app and 4 MiB in all, summed and written in one transaction. The panel names the app, so it separates nothing between apps.
- `/apps*` (`api/apps.rs`): third-party desk app packages (`docs/dev/desk-sys.md`). The operator uploads a `.fsba` (gzipped tar: `manifest.json`, `ui/**`, notices), checked whole (regular files only, plain relative paths, 2000 files, 20 MiB compressed and inflated, counted while reading) its files kept as blobs (below), waiting; approving names the package's SHA-256 and asks the password and exactly the manifest's permissions; any other package (an upload needs no password) waits again; built-in app ids are refused; removing deletes the app's storage rows. The UI is served under an HMAC launch ticket (`/apps/{id}/ui/{ticket}/…`, 12 h, bound to the package's SHA-256, key derived from the JWT secret) with `CSP: sandbox allow-scripts …; connect-src 'none'`, so it runs in an opaque origin even when opened directly. A `wasm` package adds `backend.wasm`: `POST /apps/{id}/call` runs it in wasmi (`api/app_runtime.rs`; fuel + 10 s, 64 MiB, a fresh instance per call on its own 16 MiB-stack thread) (8 at once; no re-entry into `sbm.host`; clock checked per host call); its host functions check the app's approved permission and the transport rule at the moment of use (`tests/apps_api.rs` has WAT guests).
- `/desk/themes*` (`api/desk_themes.rs`): `.fsbt` theme packages, parsed and validated by fl_lib's `fl_theme` (`packages/fl_lib/rust/theme`, the reader the app runs too). Stored as the package's summary JSON, its backgrounds as blobs; `MAX_THEMES` 32, `MAX_ACCOUNT_BYTES` 128 MiB; a newer package of the same theme id replaces the old one and keeps the selection. `desk_preferences.theme` is `<installation>` or `<installation>#<variant>`; wallpaper `theme` draws its background; removing a theme clears both. Store: the catalog (`assets/catalog/repos.toml`, bundled, also fetched) → repositories → the newest release whose schema fits; **the agent installs only an item of its own fetched catalog** (`{repo, id, version}`, never a URL from the panel) over HTTPS and checks its SHA-256; failure is `502 {error:"store", reason}`. `tests/desk_themes.rs`.

### `/api/v1/terminal/ws`

- A session is a shell the agent starts as its own user on a PTY (`pty.rs`); there is no SSH login (removed with `ssh_terminal`, migration 019). Binary frames are PTY bytes, text frames control JSON (`api/ws/terminal.rs`).
- `auth: {"kind":"local"}` is the only kind; an SSH credential (`password`/`key`/`interactive`) or an `answer` frame is refused by parsing (`bad_request`). An optional `target` narrows it, built in Rust and run via `LocalShell::spawn_command` (`/bin/sh -c`, `cmd.exe /C` on Windows): `container` (`shell_command`), `iperf` (`sbm_parser::iperf`), `tmux` / `tmux_new` (tmux's plain client; xterm.js cannot decode control mode). Refused: unknown fields (`deny_unknown_fields`), invalid values (`invalid_input` + `issue`), no runtime / no tmux (`no_container_runtime`, `no_tmux`). No frame carries a command. Panels send a target only where `features` lists `container_exec`, `iperf` or `tmux`.
- ConPTY sends `ESC[6n` and holds output until answered; Windows PTY tests use `answer_cursor_position_query`.

### `/api/v1/stream/ws` and `/api/v1/listen/ws`

- `stream`: a raw TCP connection (networking without a shell); the resolved addresses are dialled. Text frames: `{"type":"open","host","port"}` or `{"type":"accept","id"}`, then `ready`/`error`/`exit`; binary frames are bytes. One socket is one connection, no session store, no replay. The address stays out of the URL (access logs). `tests/stream_ws.rs`.
- `listen`: the agent binds (`listen` → `ready`) where the system account may, announces `incoming` with an id; the app claims it with a stream `accept`. Pending connections (`AppState.pending`) expire after `PENDING_TTL`. `tests/listen_ws.rs`.

### WebSocket traps (locked by tests)

- **Upgrades go through `api/ws/upgrade.rs`, not `ntex::web::ws::start`**: ntex caps incoming frames at 64 KiB with no setting; the copy takes 4 MiB (`MAX_FRAME`) with its own `WsSink`. TODO: back to ntex when configurable.
- **Upgrade auth is a single-use ticket** (`api/ws/ticket.rs`): purpose-bound, ~30 s, burned even on a wrong secret (no headers on a browser handshake; no token in URLs).
- **`is_secure_transport` treats loopback as secure** (same-host proxy / `cloudflared`); it never reads `X-Forwarded-Proto`.
- **Terminal sessions outlive the socket** (`api/ws/session.rs`): the handle is a 256-bit bearer capability, constant-time compared, memory-only; an `attach` takes over; detached sessions end after `detached_timeout_secs` (300). Capacity (`max_sessions`) is derived from memory.
- **Replay is incremental**: the client reports bytes rendered; `ready.since` is the absolute position the following stream starts at, and `ready` precedes output.
- **`shell` deliberately bypasses sshd** (no SSH auth, logging or 2FA; `ssh_addr` is read only by the firewall page), so `install.sh` runs the agent as an ordinary account (`systemctl --user`, or OpenRC `command_user`): that account is the reach.
- `tests/terminal_ws.rs` runs real shells on local PTYs (the account's passwd shell; `read_until` answers fish's start-up DA query).

## Configuration

- `.env` (DB URL, JWT secret, host/port, TLS) and `config.toml` (`config.json` is migrated once by `Config::legacy`; `normalize()` drops the Go keys).
- Sections are grouped by **what they act on** (`[remote_access.terminal]`, `[remote_access.fs]`, `[remote_access.exec]`, `[monitoring.extended.idle_pause]`); a key's level is a claim about its scope, and the resolved structs (`RemoteAccess` with `Terminal`/`Fs`/`Exec`) mirror it. Shared keys stay at the section level (`ssh_addr`, `allow_insecure`).
- The flat pre-Aug-2026 layout is not read (serde ignores it, so old switches revert to off — a deliberate hard cut).
- Capacities (sessions, output caps, body limits) derive from physical memory unless set; resolved values are logged at startup.
- `core/config_file.rs` writes `config.toml` atomically with bounded backups; callers hold `AppState.config_write` across read-modify-write.

### Editing it over the API

Reads go to the file on disk, not `AppState.config` (a startup snapshot). **A PUT replaces all it names**; GETs and `POST /push/test` write nothing.
- `GET/PUT /settings`: intervals, idle pause, rules, retention, CORS, `disk_counts_network` (no `jwt_secret`, `database_url`, `remote_access`). `disk_counts_network` absent from a PUT keeps the stored value. GET adds `live_fields` and `data_retention_defaults` (absent retention means no cleanup at all).
- `GET/PUT /push`, `POST /push/test` (`api/push.rs`): channels and `push_rate`. **Credentials are write-only**: GET answers `null` at credential keys (`api::push::secrets`: `sc_key`, Bark `key`/`cipher_key`, iOS `token`, every header value, SMTP and ntfy `password`, ntfy `token`, Telegram `bot_token`, Discord `webhook_url`); one is kept only while its destination keys are unchanged (`destination_keys`); a PUT `null` keeps the stored value, matched by `from_index`; `null` elsewhere is refused. A webhook `url` is not a credential. Senders live in `monitoring/push/` (one file per type); `push::validate` is what a save shares with them. `MonitorError::Http` drops the URL (it can hold a token). An unknown `push_type` is withheld and unsavable. Channels and rules apply on restart (`applies_on_restart`; TODO live, like `LiveSettings`). `tests/push_api.rs` checks the response bytes.

## Database

**Files are never stored in the database** (`core::blobs`): a wallpaper, a theme background, a desk app's files and a hosted backup are files in `blobs/` beside the database, named by SHA-256 (`<sha[..2]>/<sha>`, 0600 in 0700), and a row names the digest. A writer holds `Blobs::writing()` from `put` until the row is committed; `collect` (at start and after a delete or replace, `collect_soon`) removes what no row names, so a new table with a blob column goes into `blobs::NAMED`. A backup of an agent is the database **and** `blobs/`. Backups 0.2.0 kept in `backup_blob` move out at start (`move_database_backups`, TODO remove).

Migrations in `migrations/`: metrics history, `users` (one row since 032), `watch_tokens` (`scope` = `read`), config storage, `access_log` (audit: `kind, action, result, detail`; never a credential; retained via `DataCleanupService::POLICY_TABLES`) (`ssh_known_hosts`, the pinned key of the sshd the removed SSH terminal logged into, dropped by 019), and the feature tables named above.
