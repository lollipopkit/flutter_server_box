在构建支持的情况下，终端标签页会在你的服务器之前列出两项：**本机**的 shell，以及
ServerBox 安装的 Linux 容器。

它们排在最前面，理由和文件标签页把本机排在最前面一样 —— 它始终可达，而且不需要任何
凭据。

## 本机

运行 ServerBox 的那台机器上的 shell。在操作系统能说明你选了哪个 shell 的地方，它使用
`$SHELL`，因此和你的终端 App 打开的是同一个 shell。

可用范围：

| 平台 | 是否可用 |
|---|---|
| Linux、Windows | 可用 |
| macOS（DMG 版本） | 可用 |
| macOS（App Store 版本） | 不可用 |
| Android | 可用，不过手机上的 shell 比桌面少很多东西 |
| iOS | 不可用 |

**App Store 的 macOS 版本无法提供。** 它必须运行在沙盒中，而沙盒进程无法打开伪终端
—— 因此该入口直接不出现，而不是出现了却用不了。DMG 版本的签名不带沙盒，可以提供。
App 询问的是正在运行的进程而不是构建时写死，因此同一个二进制在两种情况下都如实反映。

**iOS 完全没有**，理由更彻底：App Store 应用根本无法启动进程，其容器内也没有
`/bin/sh` 可供启动。

## Alpine 容器

在平台不给 shell、或给的很有限的地方，ServerBox 可以安装自带的 Linux userland ——
Alpine 3.22.5，两个平台使用同一个发行版本。

它在终端标签页里显示为 **Alpine \<版本\>**，位置紧挨本机而不是混在服务器里，因为它
就是这样一个东西：同一台机器，加上这个 App 装好的一套 userland。当固定的版本比磁盘上
的更新时，该条目会提示更新。

两个平台，两套机制：

- **Android** 解包一个真实的根文件系统，用 `proot` 进入。仅支持 arm64；rootfs 是从
  网络获取后执行的 tarball，因此其摘要是固定并校验的。
- **iOS** 无法启动进程，因此它携带一个解释器，容器就是该解释器的文件系统。

**两者都只在构建包含时才存在。** 两套机制都不是默认包含的，所以一个构建可能提供本机、
提供容器、两者都提供，或者都不提供 —— 终端标签页就是按可能出现任意一种情况写的。
如果你没看到，说明你的构建里没有。

### 用来做什么

- 在没有 `curl`、`dig`、`ssh` 或 `jq` 的手机上用它们
- 不想在生产机器上做的临时操作
- 给 Agent 一个不是你自己文件系统的目标 —— 见 [Agent](/docs/zh/advanced/agent/)

它就是普通的 Alpine，`apk add` 可以正常使用。

### 它看不到什么

容器有自己的文件系统。它读不到手机存储、App 自身的数据、你的私钥和你的文件。正是这层
隔离，使得 Agent 的「在本机执行命令」开关在移动端和桌面端含义不同：在手机上它提供的是
一个沙盒，在桌面上它提供的是你的计算机。

## 与服务器有什么不同

字节流之上的一切都相同 —— 同一个终端模拟器、同一套虚拟键盘、同样的标签页。变化的只是
字节从哪里来。

本机 shell 没有需要校验的 host key，没有重连，也没有服务器卡片。它同样不会出现在服务器
列表或状态图表里：它是一个终端，不是一台被监控的机器。
