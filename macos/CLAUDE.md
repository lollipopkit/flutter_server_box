# macOS builds

Release: `make release-macos-dmg`, `make package-dmg`, `make sync-homebrew-cask`.

- **macOS ships a separate build for each architecture, selected exclusively by `ARCHS`.** `macos/Runner/Configs/Release.xcconfig` sets `ARCHS = arm64` for the App Store build; Intel users install the DMG instead. DMG builds override this value on the xcodebuild command line: `scripts/release/release-macos-dmg.sh` passes `ARCHS=` for each entry in `RELEASE_ARCHS`, while CI sets `FLUTTER_XCODE_ARCHS` for each matrix job. `flutter build macos` forwards that value because macOS has no `--target-platform` option. Xcode also passes it to the Rust build hook as `-dDarwinArchs`, ensuring that a thin app contains a thin `sbm_ffi.framework`.
  - The only macOS release assets are the notarized `ServerBox-<version>-{arm64,amd64}.dmg`. **No ad-hoc DMG is built**: an ad-hoc signature carries no keychain entitlement, so the data protection keychain refuses the first write (`-34018`) and the app stops at "could not start" (#1798). A test build is made with the release script, `PUBLISH_GITHUB_RELEASE=0` and an `ARTIFACTS_PATH` holding one architecture (no cask). fl_lib still ignores asset names containing `NoSign`, which older releases carry.
  - The Homebrew cask requires both architectures: one `arch arm:`/`intel:` declaration and two `sha256` values. `release-macos-dmg.sh` therefore skips cask synchronization unless both DMGs for the version are present. Existing artifacts may satisfy this check, allowing `RELEASE_ARCHS=arm64` to retry only one architecture.
  - **Keep `MACOSX_DEPLOYMENT_TARGET` at 13.0.** flutter_tools hardcodes `targetMacOSVersion = 13` for every code asset, so `fl_tty`, `objective_c`, and `sqlite3mc` use `minos 13.0` regardless of the project setting. A bundle that declares 12.0 can therefore contain dylibs that dyld cannot load on Monterey, as happened in the v1.0.1574 DMG. macOS 13 is also Apple's minimum requirement for dropping Intel support from the App Store build (Developer Relations, 2026-09-01). Keep the deployment target, `ARCHS`, and the cask's `depends_on macos: ">= :ventura"` aligned.
  - The macOS CI step `Check the architecture` and the release script's `verify_app_arch` both inspect `Contents/MacOS` and `Contents/Frameworks` with `lipo -archs`. This catches `native_toolchain_rust` falling back to the host when a target is missing, which could place an arm64 `sbm_ffi` in an Intel app and cause `RustLib.init` to fail. CI also launches the Intel build through Rosetta when available.
- **`FLTEnableImpeller` is a boolean written by the Runner build phase "Set FLTEnableImpeller"** from the build setting `FLT_ENABLE_IMPELLER` (`YES`/`NO`, default in `Configs/AppInfo.xcconfig`; the Intel DMG passes `NO` on the xcodebuild command line, CI as `FLUTTER_XCODE_FLT_ENABLE_IMPELLER`). Info.plist itself has no entry: `flutter build macos` reads the built plist's key as `bool?` and fails on a string, and a preprocessed Info.plist would no longer parse for flutter_tools, which reads the source plist too.
